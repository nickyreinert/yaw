# ADR-0039: cloudflare-workers profile: local-only gate (tsc, ESLint, Vitest in the Workers runtime), no remote Wrangler calls, never auto-suggested

- **Date:** 2026-10-22
- **Category:** Modules / Catalogue
- **Status:** Proposed
- **Importance:** normal

## Context

Y-6.6 adds cloudflare-workers; doc 05 lists Wrangler local (Miniflare) as dev env, tsc, Vitest (workers pool), local D1 migration and wrangler deploy --dry-run as the gate, Playwright (if UI) as screenshot, Cloudflare as deploy target, and wrangler deploy, wrangler secret and d1 ... --remote as guards. The plan row says: no remote calls in CI.

## Decision

Scaffold: one plain TypeScript Worker (src/index.ts calls src/greeting.ts, wrangler.jsonc without bindings, Vitest tests in the Workers runtime), ESLint (typescript-eslint), exact-pinned dev dependencies: wrangler 4.151.3, @cloudflare/vitest-plugin 1.4.6, vitest 5.0.5, typescript 6.0.3, eslint 10.13.0, @eslint/js 10.0.1, typescript-eslint 8.72.0 (all looked up with npm view in the registry on 2026-10-22 and installed together in a scratch project; the old package @cloudflare/vitest-pool-workers is deprecated in favour of @cloudflare/vitest-plugin, and its vitest 4.1 peer fails to resolve with npm 10.9 ('Cannot read properties of null (reading edgesOut)'), vitest 5 resolves). Gate: lint, typecheck (wrangler types writes the git-ignored worker-configuration.d.ts locally, then tsc --noEmit), test (vitest in Miniflare), npm audit --omit=dev; WRANGLER_SEND_METRICS=false is exported by the fragment. No Cloudflare account, token, login or network beyond npm; CI has no secrets. Deviations from doc 05, row updated in the same commit: (1) wrangler deploy --dry-run is not in check, the gate runs no deploy form at all; (2) no D1, R2 or KV binding and no local D1 migration yet, db-migrate prints not applicable, bindings come with the full interview (step 7); (3) no Playwright screenshot (as ADR-0036 to ADR-0038). dev runs wrangler dev --local only. deploy mirrors ADR-0036: it runs npx wrangler deploy only on the user's machine, and refuses in CI, without the argument prod and without YAW_CONFIRM_PROD=yes. Guards: wrangler-remote blocks every Wrangler form except dev, types, check, docs, --version and --help (d1, kv and r2 pass only with --local), also via npx, pnpm dlx/exec, yarn, bun x/bunx, name@version, node_modules/.bin, node .../wrangler.js, env prefixes, sudo, nohup, xargs, bash -c, chains and subshells (a package-manager install, remove, update, view or ls line naming wrangler passes); wrangler-remote-flag blocks any --remote style flag in a Wrangler command segment; just-deploy blocks just deploy, YAW_CONFIRM_PROD and npm/pnpm/yarn/bun deploy or publish; remote-host blocks ssh/scp/sftp. secretFiles adds .dev.vars and .dev.vars.<env> (template names .example, .sample, .template allowed), so the security module denies reading them. Options before the subcommand (wrangler --config x dev) are blocked as a conservative side effect. suggestWhen is empty: typescript plus serverless fits node-ts-vercel as well, and an unknown fact would suggest the profile alone, so the user picks it from the list. The scaffold and recipes read no project files, so no symlink handling is needed. CI: cloudflare-workers joins the profile matrix of kit-ci.yml (SHA-pinned setup-node and setup-just as in node-ts-vercel, no secrets); fixtures lint_error.ts and type_error.ts live in test/profiles/cloudflare-workers/.

## Consequences

A new project passes just check without a Cloudflare account; the profile is chosen manually; Wrangler remote use, deploys and secrets are blocked for the agent; wrangler dev --local was run once by hand in a scratch project (200 OK); deploy was not run in this build (it is tested only for its refusals); D1, R2, KV and the screenshot wait for later ADRs. Known gaps: wrangler options before the subcommand are blocked rather than parsed; Wrangler config with remote true on a binding is not detected by a guard (standards.md forbids it); other Cloudflare CLIs (cloudflared, C3 create-cloudflare, curl to api.cloudflare.com) are not blocked.
