# ADR-0090: Make architecture constraints follow runtime and paid-component context

- **Date:** 2026-10-29
- **Category:** Architecture / Rendering
- **Status:** Superseded
- **Importance:** normal
- **Scope:** `core/interview/**`, `core/web/**`, `core/lib/foundations.js`, `core/lib/kickoff.js`
- **Tags:** interview, applicability
- **Superseded by:** ADR-0097

## Context

Hosting and budget questions appeared for offline desktop projects and stale hidden values reached planning context. All offered languages, including Kotlin, support external dependencies.

## Decision

Use one shared runtime-context and question-applicability policy for CLI, browser, normalization, review and project planning. Hosting control applies to self-hosted, serverless, edge and static hosting, not local tools, app-store targets or plugins inside an existing WordPress site. Budget questions apply to hosting or explicitly permitted commercial dependencies/external services; a budget cap additionally requires capped cost policy. Keep dependency policy available for every offered language. Preserve in-memory edits across runtime changes but omit inapplicable constraints from saved normalized answers and generated planning/context. Preserve the separate project ground truth and generic practices.

## Consequences

A local or desktop project without paid components no longer asks about hosting or budget. Paid libraries or services can still require a desktop budget. Existing hidden constraints cannot silently govern an unrelated runtime.
