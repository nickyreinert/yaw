# ADR-0050: Local workspace dashboard (yaw web) and next steps after init

- **Date:** 2026-10-23
- **Category:** Architecture / CLI
- **Status:** Accepted
- **Importance:** normal

## Context

Issues #167 and #172: after `yaw init` users did not know how to start, where YAW keeps sessions, tasks and decisions, or how to open the web interface; `yaw init --web` was the only browser entry.

## Decision

`yaw web` opens a read-only dashboard when the folder has a YAW manifest, otherwise the setup form. The dashboard reuses the ADR-0044 form server (same token, cookie, Host/Origin and CSP rules) with a different page and one JSON route, GET /api/dashboard; it has no POST route. The data covers the project manifest and answers, TASKS.md, the decision index and session statistics from ~/.yaw/yaw.db for this project and all projects. Each section fails or reports "not available" independently; a missing registry is reported and never created. The client renders with textContent only. Both the terminal and the web init flow end with a "Next steps" block: start the selected agent, trust Codex hooks with /hooks when .codex/hooks.json is written, where tasks, sessions and decisions live, `yaw web`, `just --list`, `yaw doctor` and the tools the setup needs. Codex hook entries carry a statusMessage "YAW <module>: <hook names>" so the trust list is readable.

## Consequences

Amended: `yaw web --background` keeps one managed server per canonical folder running without an idle timeout. Subsequent `yaw web` calls reopen it with a fresh one-time link rather than starting competing servers. `yaw web --stop` stops it through authenticated local control (ADR-0044 amendment). After setup Apply, the background process starts the dashboard on the same port; reopen through `yaw web` to obtain its new session. Foreground behavior is unchanged.

Amendment: authenticated, CSRF-protected POST actions now support explicit saved session collection, manual local Laya classification, refresh preferences and personal notification settings/tests. Ordinary dashboard GETs never scan native history. Refresh-on-load is opt-in, unchecked by default and never classifies. Collection and classification persist aggregates, not message text, with explicit coverage limits. Historical sessions can appear after an import (#174) or explicit scan. No packages, model weights or services are provisioned automatically.

Overview is current-workspace-only. Global Projects/Sessions/Tasks are separate, with project filters; other-workspace tasks are explicit-collection snapshots. Knowledge is a separate personal/current-workspace section and excludes other projects' knowledge. Notification preferences are shared personal settings, while comfort enablement and the saved code map remain workspace-specific. See `docs/workspace-dashboard.md`.

Amendment (2026-10-24): one dashboard server can serve several projects. The browser tab names a `workspace` on every GET (query) and action (body); the server resolves it against a known-project list (`~/.yaw/web-projects.json` plus projects seen in saved session scans) and accepts only canonical folders that contain a YAW manifest, otherwise 404. The sidebar switcher keeps the choice per tab; an "Add project folder" action (`project-add`) admits a new folder under the same rule. Knowledge create/edit/delete actions are described in ADR-0053.

The cookie-port limitation of ADR-0044 applies to the dashboard too. Changing a hook label changes its hash, so Codex asks for trust again.
