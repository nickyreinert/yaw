# ADR-0044: Local form server: one-time start token exchanged for an HttpOnly session cookie, X-YAW-Token header on POST, Host and Origin allowlist, 30 min idle

- **Date:** 2026-10-22
- **Category:** Architecture / CLI
- **Status:** Proposed
- **Importance:** normal

## Context

Y-7.3 (#72) needs a local server for the browser form (doc 02, doc 08). The docs fix 127.0.0.1, random port, one-time token, Host/Origin checks, CSRF protection, 30 min idle and no external assets, but not how the token travels or how CSRF is checked.

## Decision

core/web/form-server.js, node:http only, listens on 127.0.0.1 with a random port. Token: the printed URL carries a 256-bit start token (/?t=...); it is valid for one GET, compared with timingSafeEqual, and answered with 303 to / plus a random session secret in an HttpOnly, SameSite=Strict cookie, so the token leaves the URL and history. The cookie has a Max-Age in whole seconds, rounded down from the configured idle timeout, so it never lasts longer than the server's idle timeout. Every other request needs that cookie. CSRF: every POST also needs the header X-YAW-Token equal to the session secret (embedded in the served page as a meta tag); a cross-site form cannot set a custom header and a cross-origin fetch with it triggers a preflight that the server does not answer. GET and HEAD never change state; other methods get 405. Host must be 127.0.0.1:<port> or localhost:<port> (else 421); Origin, when present, must be http:// of those (else 403). Idle timer 30 min, reset on every request, injectable for tests; SIGINT closes the server. Responses carry Content-Security-Policy default-src 'self', no-store and nosniff; no external URL anywhere. Nothing is logged and no file is written.

## Consequences

A link preview or a second tab that opens the start URL first consumes the token; the user restarts the command. The session lives until shutdown (no rotation). There is no POST endpoint yet (404 after the checks); Y-7.4/7.5 add them and the CLI entry (yaw init --web). Cookies ignore the port: any other HTTP server on 127.0.0.1 that the browser visits receives the session cookie, and the cookie value is also the X-YAW-Token, so such a server could act as the user. Mitigation is short-lived sessions and the loopback-only bind; it is not closed. A request with zero or several Host headers gets 400, a malformed request target 400, and only authenticated requests reset the idle timer. Node defaults apply for connection timeouts (headersTimeout 60 s, requestTimeout 300 s, keep-alive 5 s). Doc 02 section 3 and doc 08 section 3 follow.

## Amendment: concurrent browser sessions and opt-in background lifetime

Each server uses a random cookie name, preventing another YAW instance on the same loopback host from overwriting its cookie. This does not isolate cookies from other loopback servers: the disclosure limitation above remains. Authenticated requests renew the cookie's idle-bounded lifetime. A browser that already has a valid session can revisit a consumed launch URL; an unauthenticated replay is still refused.

`yaw web --background` explicitly opts out of the idle deadline. It starts a detached, loopback-only process per canonical project folder. Private state and a private browser launcher live in `~/.yaw/web/` (directory 0700, files 0600); stderr goes to a private log there. Credentials do not enter process arguments. Cookie lifetime in this mode is the browser session. The CLI uses a separate random control secret and POST-only `/api/web/open` and `/api/web/stop` routes, still subject to Host/Origin checks, to obtain a fresh one-time link or stop the server. An ordinary browser cookie is insufficient for control. A refused control request never triggers process replacement or a PID signal. Only connection refusal is treated as stale state, with an explicit CLI notice. SIGINT and SIGTERM clean up state. Reopening uses `yaw web`; stopping uses `yaw web --stop`. Foreground servers retain the 30-minute idle shutdown.
