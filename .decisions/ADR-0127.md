# ADR-0127: java-serverless profile: Java x serverless with hosting variants container and lambda (T-001)

- **Date:** 2026-10-31
- **Category:** Modules / Catalogue
- **Status:** Accepted
- **Importance:** normal
- **Scope:** `profiles/java-serverless/**`

## Context

T-001: Java x serverless. Pattern: ADR-0119 (kotlin-serverless), ADR-0126 (java-web). Cited ADR-0116 (tools list), ADR-0105 (profile options).

## Decision

- java-serverless takes java x serverless. Option hosting (default container) selects variants/<choice>/; scaffold/ holds the wrapper, settings, Greeting.java and the shared pure Routes.handle with its test.
- container: Server.main on the JDK HTTP server (HOST/PORT, graceful stop), Dockerfile, .dockerignore, no libraries. lambda: class Handler implementing RequestHandler<APIGatewayV2HTTPEvent, APIGatewayV2HTTPResponse> (handler com.example.app.Handler::handleRequest) delegating to Routes.handle; tests call it directly. No SAM template: deployment is the user's.
- Pins, exact: aws-lambda-java-core 1.4.1 and aws-lambda-java-events 3.16.1 (lambda). Lambda package: a buildZip task (classes at top level, runtime libraries in lib/), run by build, written to build/distributions/app-0.0.0.zip.
- Tools (ADR-0116) for lambda: aws and sam. Same gate as java-cli for both. dev: gradlew run (container) or a note (lambda). Guards: gradle publish, registry pushes, aws/sam/gcloud, release tags, remote hosts. CI: examples java-serverless and java-serverless-lambda join the kit-ci matrix.

## Consequences

Both flavors pass just check offline of any cloud. The Dockerfile and the Lambda deployment (runtime java17, handler string, API Gateway payload format 2.0) are never run by the kit, so they are unverified. Blocking all aws/sam/gcloud commands also blocks read-only calls. JDK 17 minimum is checked in CI only.
