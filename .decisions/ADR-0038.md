# ADR-0038: wordpress-plugin profile: gate without Docker (WPCS, PHPStan, PHPUnit), wp-env and Plugin Check on demand, never auto-suggested

- **Date:** 2026-10-22
- **Category:** Modules / Catalogue
- **Status:** Proposed
- **Importance:** normal

## Context

Y-6.5 adds wordpress-plugin; doc 05 lists `wp-env` (Docker) as dev env, PHPCS + WPCS, PHPStan (WP stubs), PHPUnit, Plugin Check and `composer audit` as the gate, Playwright against wp-env as screenshot, ZIP release / WordPress.org SVN as deploy, and SVN commit and prod DB ops as guards. The plan row asks for `wp-env` in CI.

## Decision

Scaffold: one plugin (main file with header and an ABSPATH guard, a shortcode, pure logic in `src/` with namespace `MyPlugin`), `readme.txt`, PHPUnit tests that need no WordPress, `phpcs.xml.dist` (WordPress ruleset, text domain, PSR-4 file names allowed), PHPStan level 8 with `szepeviktor/phpstan-wordpress` (WordPress stubs, included by path, no extension-installer plugin), `.wp-env.json`. Exact-pinned dev dependencies, resolved and run with PHP 8.2 and Composer 2: wpcs 3.4.1 (needs PHP_CodeSniffer 3.x; PHPCS 4 is not yet supported by WPCS), dealerdirect/phpcodesniffer-composer-installer 1.2.0 (the only Composer plugin, allowed by name in `allow-plugins`), phpstan 2.1.56, phpstan-wordpress 2.0.4, phpunit 11.5.57. Gate (`just check`): phpcs, phpstan (memory limit 1G for the stubs), phpunit, `composer audit --locked`; no Docker, no WordPress download, no database, no network beyond Composer/Packagist.

Deviations from doc 05, with the doc row updated in the same commit:
- Plugin Check is not in `check`: it runs inside WordPress, so it needs wp-env (Docker plus a WordPress download, network beyond the package manager). It is not a verb (the uniform verb set stays fixed): the user runs `npx @wordpress/env run cli wp plugin install plugin-check --activate` and `wp plugin check <plugin folder>` in wp-env, which `just dev` starts (pinned `@wordpress/env@12.0.0`). `just dev` and Plugin Check were not run in this build.
- `wp-env` is on demand (`just dev`), not in CI: the CI job runs `yaw init` + `just check` like the other profiles, which needs no Docker. This replaces the plan wording "`wp-env` in CI".
- No Playwright screenshot against wp-env (as in ADR-0036, ADR-0037); `screenshot` prints not applicable.
- No ZIP release recipe: `build` prints not applicable and `deploy` only prints a note. A ZIP script would read project files and need symlink handling; it waits for a later ADR. The scaffold has no scripts that read project files, so no symlink handling is needed.

Guards (tested against bypass forms: env prefixes, `--username`-style option prefixes, sudo, env, nohup, time, xargs, bash -c / sh -c, npx/pnpm/yarn/bunx runners, chains, subshells): `svn-write` blocks every SVN write (`commit`, `ci`, `import`, lock, property and patch commands, `svnmucc`, `git svn dcommit`, and delete/copy/move/mkdir against a URL) in any position after `svn`; `deploy-script` blocks running a deploy/release/publish script (`deploy.sh`, `./bin/release.py`, via an interpreter or wrapper) and task-runner targets named deploy, release or publish (`npm run`, `composer`, `make`, `just`, `task`, `npx`); `wp-cli-remote` blocks wp-cli with `@alias`, `--ssh`, `--http` and `db reset|drop|import|clean|repair`; `remote-host` blocks ssh/scp/sftp/ftp/lftp and rsync to a host. Allowed: `svn status/update/checkout/diff/log/info/add`, `cat deploy.sh`, `git add deploy.sh`, `npm test`, `wp plugin list`, `wp db export`, `wp-env start`, local rsync. Limit: the SVN pattern looks for the subcommand anywhere in the same command segment, so `svn log` with the word `commit` as an argument is also blocked.

suggestWhen is empty: the interview has no WordPress or PHP fact (language choices are python, javascript, typescript, auto), so no fact is narrow enough and the user picks the profile from the list.

CI: wordpress-plugin joins the profile matrix of kit-ci.yml, which already has the SHA-pinned setup-php step (PHP 8.2, Composer 2, no coverage); fixtures `lint_error.php` and `type_error.php` live in test/profiles/wordpress-plugin/.

## Consequences

A new project passes just check without Docker or WordPress; the profile is chosen manually until the interview knows WordPress; SVN releases, deploy scripts and remote wp-cli are blocked for the agent; Plugin Check and the dev site run only when the user starts them; the smoke test is skipped where php or composer is missing.
