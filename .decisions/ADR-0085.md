# ADR-0085: Distinguish YAW profile coverage from runtime capability

- **Date:** 2026-10-28
- **Category:** Architecture / Rendering
- **Status:** Accepted
- **Importance:** normal
- **Supersedes:** ADR-0054
- **Scope:** `core/interview/**`, `core/web/**`, `profiles/static-site/**`
- **Tags:** stack, profile, interview

## Context

The stack interview called every missing profile impossible, including browser frontends on local, self-hosted, serverless and edge hosting.

## Decision

Keep the language and hosting questions, one profile per pair, shared deterministic selection in CLI and web, and module card metadata from ADR-0054. Profile absence means this kit has no setup for the pair, never that the language cannot run there. The static-site profile covers browser HTML/CSS/JavaScript on local, self-hosted, serverless-platform, edge/CDN and static hosting. Profile metadata supplies target-specific guidance in both interfaces; function code and provider configuration are separate work. Keep WordPress and app packaging uncovered until a matching profile exists. Preserve existing stored language IDs.

## Consequences

Frontend hosting selections work without claiming that a static scaffold provisions functions or an edge runtime. Existing static-site lint and audit choices from ADR-0034 remain. New profiles must keep pairs unique; both interfaces and generated files must remain in parity.
